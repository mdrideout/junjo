## Messaging baseline to preserve

1. Junjo supplies a Python SDK **inside the application** and a separately deployed **Junjo AI Studio telemetry and evaluation observation service**.
2. The coding agent investigates, develops, orchestrates experiments, and proposes changes. The application executes targets, model calls, and evaluators. Studio stores/query-enables datasets, outcomes, and execution chronology for coding agents and humans.
3. Recursive self improvement means an evidence-grounded software development cycle: find failure modes, establish criteria, generate/curate cases, run the application, compare outcomes, inspect traces, and iterate.
4. Natural-language prompts and skills make that cycle accessible through the user's coding agent. Studio is not the scheduler or a hosted code execution service.
5. Adopt telemetry around existing code/frameworks; optionally use SDK workflows, specialist agents, concurrency, and state to decompose complex work. Do not imply migration to a Junjo agent runtime is required for all observability.
6. OpenTelemetry is the boundary. Available evidence depends on emitted instrumentation; raw trace storage does not automatically imply native Junjo graph/state diagnostics.
7. Datasets, runs, evaluator evidence, and links to Studio allow both agent and human to investigate the same record. Comparison is evidence about tested scenarios, not a universal guarantee of quality or zero regressions.
8. Smaller/faster/cheaper specialized execution is a goal to evaluate, not an automatic outcome. Parallelism and schedules run through application/agent orchestration and real resource constraints.
9. OpenAI Agents SDK is the released reference integration. Other advertised frameworks are coming soon; Python support and broader OTLP ingestion must not be conflated with released language SDKs or native adapters.

### Cross-page findings established so far

- **F01 — Adoption gap (high):** The homepage promise is “keep your stack and ask your coding agent.” The docs home partially delivers that, but the main next step is a new graph tutorial. Missing: a single first-success journey with SDK/service placement, the two credentials, skill discovery, existing framework telemetry, one failure scenario, and a linked comparison report.
- **F02 — EDD positioning drift (high):** Python overview and the EDD landing page still equate Junjo evaluation with pytest and local fixtures. That remains a valid optional technique, not the definition of the shipped `EvaluationHarness` + Studio dataset/run system. Make recursive self improvement the conceptual entry point; present EDD as its evaluation method and link detailed mechanics rather than maintaining two competing definitions.
- **F03 — Tutorial payoff gap (medium):** Core teaching pages end after constructing/running primitives. Add a short application-quality task and next link into observation/evaluation; preserve necessary API detail and avoid duplicating the whole homepage on each page.
- **F04 — Page metadata and topic identity (medium):** Live crawl found **10 of 20 narrative pages without a meta description**, including Python overview, agents, agent composition/testing, evaluation, quickstart, EDD, visualization, deployment, Docker reference. Generic titles dilute topic clarity. All 216 docs have titles/H1s/self-consistent canonicals; no missing canonical fix is needed. All 216 lack `og:image`: optional shared documentation card + page-specific social titles would improve sharing, not a claimed search-ranking fix.
- **F05 — Honest evaluation boundaries (high):** Keep generated output separate from correct answers, calibrate judges, report errors and coverage separately, and describe results as evidence for tested scenarios. The current-source calibration additions are useful but not yet shipped in the stable pages. Do not turn a finite evaluation into a promise to handle every possible case.
- **F06 — Missing operational RSI guide (high):** The homepage now shows scheduled and parallel improvement loops. Docs need the exact application/agent-owned mechanics: harvest observed failures, author criteria/cases, lock a comparable dataset, commit candidate code, run new experiments, inspect cases, and share evidence. Separate independent parallel Runs from the explicitly sequential `EvaluationExecutor`; Studio stores results, it does not schedule or execute code.
- **F07 — Shared evidence handoff gap (high):** Explain how an agent produces a report with deep links that a human can open to the same case, attempt, trace, span, or state diff. The platform promises this strongly, while most guides stop at CLI output or “View spans.” Supported routes are verified in the evidence-link section below; teach run/comparison/execution links and within-view case/state inspection rather than inventing dedicated attempt/state-update URLs.
- **F08 — Stable versus current documentation (high):** Only two narrative Python pages differ from the currently released docs: `evaluation.md` (CLI explainer, staged evidence, judge guidance) and `testing/eval-driven-development.md` (judge guidance). Studio public prose is identical. A website-only release does not publish unreleased SDK doc updates. Coordinate source edits with the appropriate SDK/Studio docs release selection.
- **F09 — Specialist improvement story missing (medium):** Agent pages teach runtime structure and maintainers' invariants, not how independent prompts/tools/inputs/datasets let a coding agent improve one specialist and check E2E impact. Keep deterministic unit testing and live behavioral evaluations distinct and connected.
- **F10 — Integration page needs an adoption example (medium):** The flagship external-framework guide has good contracts but no compact runnable wiring. Treat model-provider freedom, framework integration, generic OTLP ingestion, and native Junjo diagnostics as separate capabilities.
- **F11 — Defensive rhetoric (low):** Overview emphasizes what competing abstractions allegedly do wrong. A clearer fit with “keep your libraries” is the concrete promise that execution remains explicit and application-owned. Verification note: an initial draft suspected a `@StoreAction` contradiction; source inspection found no such public decorator. That suspicion was removed and is not an audit finding.

## Strategic recommendation: make the docs fulfill the homepage promise

The documentation is **partially aligned**, with good separation of responsibilities and solid technical contracts, but it still introduces much of Junjo as a graph SDK with a visualization companion. The homepage now introduces an application-improvement platform: the coding agent can investigate, change, rerun and explain results using shared evidence.

Do not rewrite the entire reference into marketing. Change the path through the material:

**Connect Junjo → investigate a real failure → establish cases and judges → compare a targeted change → show the evidence → improve the implementation further.**

### Preserve

- SDK/app/Studio ownership, application-local execution, explicit model/provider choices, and the additive OpenAI integration.
- Typed state, atomic commits, immutable graph definitions with dynamic traversal, cancellation and failed-execution identity.
- Generated outputs are observations rather than automatically correct answers; locked cases; failed judgments versus operational errors; coverage and pass-rate distinctions.
- Source-owned exports, stable version selection, good canonical links and functional internal anchors.
- Useful detailed API and deployment material. Move it behind the appropriate task; do not replace it with broad RSI claims.

### Add one primary guide: “Recursive self improvement with your coding agent”

Suggested route: `/docs/recursive-self-improvement/` (new platform guide owned by the website). Its job is to turn the hero into a working, inspectable outcome. It should link exact commands and contracts to SDK-owned documentation rather than duplicate their implementation reference.

1. **Explain the boundary immediately.** Python SDK in the application; Studio deployed alongside it; the preferred coding agent remains in control. Briefly define RSI here as iterative software improvement grounded in execution evidence, not autonomous model-weight training.
2. **Connect once.** Point to setup for the SDK/instrumentation, Studio, developer access token and telemetry key, application targets/evaluators, and the released skill. Identify the supported existing-framework path. Finish setup with a visible trace and a readable dataset/run.
3. **Use a concrete prompt.** “Use Junjo to investigate recent refund failures, add scenarios that reproduce them, evaluate a targeted fix, and show me the comparison and execution evidence.” Include the user's chosen scope for edits/commits; explain that the prompt operates an established integration, not a magic zero-setup service.
4. **Demonstrate a real failure.** Show an observed incorrect refund decision, its intermediate policy/state evidence, and the selected failure mode. Protect or redact customer data in the example. Identify what instrumentation is actually available.
5. **Establish the comparison.** Author or generate cases and explicit criteria, calibrate a model judge if used, then lock the dataset. If an old dataset is already locked, create the revised dataset and run both baseline and candidate against it. Do not append a case to a locked dataset or compare unrelated case sets as if identical.
6. **Make one change.** Change a prompt, route, state update, or focused operation; use the clean committed revision required by the normal CLI. Rerun and inspect passed, failed and error cases with coverage. A failure/error is useful evidence, not something to omit from the story.
7. **Return evidence to the human.** Give the result report and actual supported Studio deep links. Explain any remaining failures and what the experiment does and does not establish.
8. **Continue to richer improvements.** Link to splitting a monolithic step, independently evaluating a specialist, concurrent work, model-adapter choices, and externally scheduled/parallel experiments.

Keep recurring and parallel RSI as practical extensions of this guide first. They can become their own pages once an end-to-end runnable example warrants it. Use independent run identities and clean worktrees, and state that the coding-agent scheduler/automation owns execution. Do not describe Studio as a scheduler or the sequential executor as a distributed worker queue. “Parallel improvements” describes the usage pattern; it is not an assertion of benchmarked unlimited infrastructure capacity.

### Give existing guides distinct jobs

- **Dataset/run guide:** How repeatability and comparison work. Cases, targets, criteria, judges, locking, results, scope, evidence readiness, and exact CLI/Python behavior. This is a supporting mechanism for RSI.
- **Eval-driven development guide:** How to design meaningful evaluations and combine them with local deterministic tests. Keep the existing term/URL, but stop presenting pytest as the definition of Junjo's evaluation product. Do not promote it ahead of RSI in the primary navigation.
- **Studio guide:** How both coding agent and human investigate the same record. Data → comparison → case → execution → intermediate operation/state → evidence link. Setup belongs in Deployment.
- **Building-block guides:** What can be changed and independently evaluated. A node, specialist, conditional graph, concurrent group or subflow is a concrete improvement boundary, not just a diagram primitive.
- **Integration guide:** How Junjo fits inside an existing application framework. Observe the outer agent, optionally call a Junjo workflow/specialist tool, evaluate the outer or inner target. Keep the Python support status explicit.
- **Model-driver recipe:** How to retain the chosen provider SDK/library when using a native Junjo Agent. This is different from a framework integration and should not suggest official adapters for every homepage logo.
