# Junjo Release Descriptions

## Outcome

Produce an accurate release page that quickly explains what the component is,
what people can now accomplish, what changed for existing users, and where
technical readers can verify the release. Preserve the release transaction and
its provenance evidence.

## Scope and authorization

- Treat the Python SDK and Studio as independently versioned products with
  namespaced `sdk-python-v*` and `studio-v*` tags.
- When a request refers to the latest Junjo releases, inspect the live release
  list and normally handle the newest stable release for each named or active
  component. Do not rewrite older releases unless requested.
- Drafting and review are read-only. Change a live GitHub description only when
  the user asked to create, improve, update, or publish it.
- Edit only the requested release body. Do not create or move tags, create or
  republish releases, change release state or title, upload or remove assets,
  or mark a different release as latest unless explicitly requested.
- Never use `gh release create` merely to add a description. Publishing an SDK
  release triggers the PyPI workflow; description work must not initiate a
  release transaction.

## Establish the shipped facts

1. Read the root `AGENTS.md` and the scoped owner guidance for any component
   whose behavior must be interpreted.
2. Inspect the live release body and metadata with `gh release list`,
   `gh release view`, or the GitHub API. Confirm the exact tag and target
   commit before writing.
3. Compare the release tag only with the previous tag in the same namespace.
   Never let a Studio tag become the SDK comparison base, or vice versa.
4. Read evidence at the release tag, not only the current worktree:
   - SDK: `sdks/python/CHANGELOG.md`, its README, shipped guides, examples, and
     relevant public tests.
   - Studio: the tagged diff, `apps/studio/README.md`, deployment READMEs,
     accepted ADRs, user-facing frontend behavior, and relevant tests.
   - Paired versions: `tooling/docs/stable-releases.json` and the canonical
     deployment distributions.
   - Product language: the tagged component README and public website source.
5. Treat post-tag commits as unreleased. Every product claim, compatibility
   statement, removal, and upgrade warning must be supported by the tagged
   release.
6. For Studio, preserve the validated source, workflow, image digests,
   distribution hashes, mirror revisions, and attached release evidence. The
   deterministic evidence generated by
   `tooling/scripts/build_studio_release_evidence.py` is provenance, not
   editorial copy.
7. Verify operational instructions against the actual tagged configuration,
   Compose mounts, migrations, and deployment behavior. If documentation and
   implementation disagree, state only the confirmed high-level warning in the
   release and report the discrepancy separately; do not invent a procedure.

## Write for product understanding

Lead with a short explanation of the component and the release outcome. Prefer
what a person can do over internal implementation details.

- Translate capabilities into recognizable work: establish a quality
  baseline, compare a candidate, inspect a failed case, follow an AI decision,
  or connect an existing framework.
- Define specialized terms on first use. For example, describe an evaluation
  as repeatable real-world test cases and a trace as the step-by-step execution
  record behind a result.
- Explain ownership when it affects expectations. For Studio-connected
  evaluation, application code and credentials remain in the application
  environment while Studio stores results and evidence.
- Put destructive resets, data incompatibility, removals, security changes,
  and required paired upgrades near the top. Do not bury them in a changelog.
- Separate product highlights from exact developer or operator migration notes.
- Link the paired component release when the experience spans SDK and Studio.
- Link the tagged technical changelog and a same-namespace GitHub comparison.
- Keep deterministic Studio release evidence verbatim in a clearly labeled
  technical section, usually a collapsed `<details>` block.
- Retain useful existing information unless it is inaccurate or superseded.
- Avoid hype, unexplained acronyms, commit-message paraphrases, and claims such
  as unlimited, effortless, secure, or production-ready unless the tagged
  evidence proves the specific claim.
- Do not use an autogenerated comparison link as the entire description.

Use the smallest Markdown structure that makes the release easy to scan. The
release does not need identical headings or a fixed number of bullets when its
actual content calls for a different shape.

## Publish safely

1. Recheck the proposed body against the exact tag and current live body.
2. For an already published release, update the body with `gh release edit`
   without passing flags that alter the title, state, assets, or latest marker.
3. Update each requested component release independently so a failure is
   visible and recoverable.
4. Read the saved release back through the GitHub API. Verify the tag, title,
   links, warnings, technical evidence, and body, and confirm that assets and
   release state were not changed.
5. Report the updated release links and the material editorial changes. Report
   any documentation or implementation drift discovered during verification
   as a separate follow-up; do not silently expand scope into repository edits.

## Review standard

A description is ready when a nontechnical reader can explain why the release
matters, an existing user can find every material upgrade risk, a technical
reader can reach the exact details, and every statement is traceable to the
tagged product or release evidence.
